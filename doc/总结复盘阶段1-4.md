# Relay 项目复盘(阶段 0 – 4)

## 阶段 0:规划与环境

**目标:** 建立项目全景认知和心智模型。

**设计思路:** 先立核心理念——"Agent 的执行不是内存里的循环,而是数据库里的一串事件"(事件溯源 + 持久化执行)。所有后续设计都从这句话推导。技术选型确立三原则:兼容标准接口、少传递依赖、社区长期维护。

**亮点:** monorepo + git 从第一天开始;每阶段结束都有能跑的东西,避免"写两周看不到效果"。

**沉淀原则:** 架构理念先行,选型有明确的判断标准而非跟风。

## 阶段 1:Go 服务骨架

**目标:** 生产级 HTTP 服务的地基:健康检查、结构化日志、优雅关闭、中间件、配置管理。

**设计思路:** "服务在 goroutine 里跑,主线程做信号哨兵"的标准骨架;中间件洋葱模型(注册顺序 = 请求穿透顺序);配置启动时一次性加载并校验(fail fast);依赖注入用最朴素的形态——函数参数和结构体字段,不用框架。

**亮点:**
- 手写请求日志中间件,吃透了 `WrapResponseWriter` 包装模式(中间件如何观测只写的 ResponseWriter)
- RequestID 建立关联(correlation)概念——并发日志按请求归组,可观测性第一块砖
- 你发现了 `RealIP` 的官方漏洞警告(IP spoofing),我们由此学了**信任边界**:跨边界的数据不可信,除非能验证来源;并修正了"早加免得忘"的错误建议——涉及信任的东西恰恰要等清楚部署拓扑再配

**难点:** 理解 context 的双重角色(取消信号传递 + 请求域值携带);中间件顺序的推理(Logger 在 Recoverer 外层,panic 的请求才不会从日志里消失)。

**沉淀原则:** fail fast;预期错误与真错误分类处理(`http.ErrServerClosed`);密钥永不进日志。

## 阶段 2:数据模型与事件溯源地基

**目标:** pg + pgxpool + goose + sqlc 的完整数据层,runs/events 两张表,第一个业务 API。

**设计思路:** **events 是唯一真相源(append-only),runs 是投影**——这是全项目最重要的一个设计决策。`UNIQUE(run_id, seq)` 一行约束同时买到严格有序和幂等写入。工具链哲学:sqlc"你写 SQL 我生成类型",与 ORM 相反,SQL 和 Go 都是白盒。

**亮点:**
- 生产级连接池参数逐项讲透:MaxConns 宁小勿大、Lifetime 加抖动防惊群、fail-fast ping
- liveness(/healthz)与 readiness(/readyz)分离——DB 抖动不该导致进程被编排系统误杀
- 故障演练进入习惯:stop postgres 看 503,验证失败路径而不只是成功路径
- 双 ID 设计:全局 BIGSERIAL(SSE 游标)与 run 内 seq(排序+幂等)各司其职
- handler 层的生产细节:MaxBytesReader 防 DoS、DisallowUnknownFields 快速暴露集成错误、nil slice 返回 `[]` 不返回 `null`、内部错误进日志/模糊错误给客户端

**难点/踩坑:** `missing go.sum entry`(理解 go.mod 清单 vs go.sum 防伪锁,`go mod tidy` 反射);JSONB→`[]byte`→Base64 的序列化陷阱(`json.RawMessage` + sqlc override 解决,教训:"数据坏了"先分辨是存储坏了还是边界表示错了)。

**沉淀原则:** 演进式架构(没有复杂度不预建楼层);TIMESTAMPTZ 永远;迁移不可变;RETURNING 一次往返拿回数据库生成值。

## 阶段 3:最小 Agent 循环

**目标:** LLM 客户端(手写 OpenAI 兼容协议)、工具系统、引擎主循环——Relay 从 CRUD 变成 agent。

**设计思路:** 三个"意图与执行分离"层层递进:模型不拥有工具,只生成调用意图,执行权在引擎;tools 数组是每次请求"借"给模型的能力清单(无状态带来动态工具集的自由);引擎是意图↔执行的调度者。**buildMessages 每拍从事件流重建对话,不维护内存态**——恢复逻辑与正常逻辑是同一段代码,为阶段 4 铺平一切。

**亮点:**
- 依赖协议不依赖厂商(换 hy3 零代码改动,命名用 LLM_ 前缀反映抽象层级)
- 工具错误哲学:**"执行了但失败"是给模型看的数据,"没能执行"才是给引擎看的错误**——agent 的自我纠错能力建立在它能看到自己的失败上;模型幻觉出不存在的工具同样作为对话内容反馈
- 路径沙箱:规范化后白名单前缀检查(含 `workspace+分隔符` 防兄弟目录绕过),黑名单思维 vs 白名单思维的实例教学
- 从第一天采集 usage tokens——阶段 4 压缩的数据基础

**难点/踩坑:** `arguments` 是"内容为 JSON 的字符串"要二次解析且可能不合法;.env 排障两连(工作目录/文件内容/加载顺序的排查模板;Go 字段名 vs 环境变量名的三层名字映射);symlink 是字符串检查的盲区(记账:os.Root)。

**沉淀原则:** 给模型写工具 description 是写 prompt 不是注册回调;确定性是隐性需求(Registry 保序);Registry 注册冲突 panic——错误分类决定处理方式。

## 阶段 4:可靠性核心(Relay 的灵魂)

**目标:** 恢复、重试、压缩、取消、挂起、熔断六件套。

**设计思路:** 每个机制都是对一类具体故障的回答,且全部搭在阶段 2/3 的地基上:

| 机制 | 故障 | 核心手段 |
|---|---|---|
| 崩溃恢复 | 进程死亡 | 孤儿扫描 + 事件重放 + 唯一约束幂等(23505=信号非故障) |
| 重试退避 | 网络/限流瞬态失败 | 错误分类 + 指数退避 + 全抖动 + select 可取消等待 |
| 上下文压缩 | token 无限增长 vs 有限窗口 | compaction 也是事件;给模型的视图有损,系统记忆无损 |
| 取消/挂起 | 用户反悔 / 进程要关 | Runner(map+Mutex+WaitGroup)+ 协作式取消;挂起=留 running 白捡恢复 |
| 死循环熔断 | agent 原地转圈 | 连续相同工具调用签名计数;宁可晚触发不误杀 |

**亮点:**
- **故障注入成为验证方法论**:kill -9 看恢复、flaky 桩看重试叙事、错 key 看不重试——每个机制都被亲手打断验证过
- 长任务可靠性的数学:0.99⁵⁰⁰≈0.66%,重试把单步失败率压到指数爆炸救不回的程度
- 架构自洽的红利反复兑现:压缩生效零特判(下一拍重建自然采用)、compaction 崩溃自动正确、挂起功能几乎白捡
- 4.2 的配置事故复盘范本:找根因(.env 不跟机器走)、挖深层(启动校验欠账)、辨误伤(url.Error 被误分类)、也确认防线正常工作(错误链完整、失败有尊严)

**难点:** 协作式取消的完整链条(cancel=close channel → 三类检查点消费 → 错误沿 %w 链流回 → errors.Is 辨认 → 按意图写状态 → goroutine 自然消亡);cancel 与 goroutine "绑定"的真相(共享 channel + map 记账的人为约定);收尾写库必须用新 context;at-least-once 语义对副作用工具的遗留问题。

**沉淀原则:** 同步是分布式系统的敌人,抖动是便宜解药;策略与机制分离(重试放调用点);取消优先于一切机制;一切阻塞点必须可取消;配置不是免费的(该进 env 的判断标准)。

