# Relay 项目复盘(阶段 5 – 6)

## 阶段 5:实时推送 + React 前端

**目标:** 让系统"看得见"——SSE 实时推送事件流,React 前端呈现 Run 列表与实时执行时间线。

### 设计思路

**核心决策 1:SSE 而非 WebSocket。** 需求本质是服务器单向推送,WebSocket 的双向能力过剩且带来独立的协议/鉴权/心跳/重连体系。SSE 是"一个永不结束的 HTTP 响应"——复用全部现有中间件,浏览器 `EventSource` 原生自动重连。**按需求形状选协议,不按流行度选。**

**核心决策 2:实时通道允许不可靠,持久层兜底。** 进程内 pub/sub(Bus)负责"提醒",数据库负责"真相"。慢消费者的 channel 满了直接丢(`select+default` 非阻塞发送)——绝不让一个卡住的浏览器拖死引擎。丢失的推送由重连补发机制找回:全局 BIGSERIAL `events.id` 做游标,浏览器自动带 `Last-Event-ID`,服务端 `ListEventsAfter` 补发。**2.2 设计双 ID 时预留的座位,在此入住。**

**核心决策 3:数据形状决定同步机制。** 列表页是"状态快照"→ Query 轮询(且智能:有活跃 run 才轮询);详情页是"append-only 增量序列"→ SSE。两条通道互相触发:事件流里的 `run_finished` 就是"该刷新 run 状态了"的信号,精确 invalidate。

### 亮点

- **"先订阅,再查历史"** 的顺序防丢事件:反过来存在时序漏洞(盘点后、开门前写入的事件永久丢失)。宁可重复不可遗漏,重复靠全序 id 去重——这是所有"快照+增量"系统(CDC、Kafka 消费者)的同一个经典问题和同一个答案
- **去重在每一跳重复出现**:服务端 `lastSent`、客户端 `prev[last].id` 判断完全同构——分布式系统里每一跳都可能重复投递,每一跳都要防
- **心跳不是装饰**:20 秒一行 SSE 注释,防中间设备掐空闲长连接——与 2.1 连接池 MaxConnIdleTime 同源的认知(长连接的敌人是中间设备)
- **时间线回放零成本**:点开历史 run,完整执行过程瞬间呈现——规划时承诺的"事件溯源的天然福利"兑现,没写一行专门的回放代码
- **三机制联合演出**:执行中重启后端 → 挂起恢复(4.4)+ SSE 补发(5.1)+ 前端去重(5.3)无缝衔接,断线不丢不重
- 前端工程纪律与后端镜像:错误规范化放边界层(`request<T>` 对 fetch 不 reject 4xx 的坑统一处理 ↔ 后端 `writeError`);缓存失效优于缓存修补(`invalidateQueries`,数据流单向:服务器→缓存→视图);`EventCard` 的 default 分支前向兼容(对未知事件类型降级不崩溃)
- Vite 代理而非 CORS:开发与生产的请求路径完全一致(都是相对路径 `/api`),**消除差异优于处理差异**

### 难点/踩坑

- **latest-ref 模式**:回调直接进 useEffect 依赖 → 父组件每次渲染 → effect 重跑 → SSE 疯狂断连重连。用 `useRef` 承接最新回调,effect 只依赖 `runId`——React hooks 处理"依赖里有函数"的经典手法
- **cleanup 泄漏链**:忘写 `es.close()` → 前端连接泄漏 → 服务端 Bus 订阅者泄漏。前后端的资源释放通过 `r.Context().Done()` + `defer unsubscribe()` 握手
- Bus 退订函数负责清 map,防订阅者累积

### 沉淀原则

- 一份历史,多种视图:`buildMessages`(投影成 LLM 对话)与 `EventCard`(投影成 UI)是同一模式的两个 switch
- 声明式优于命令式:Query 的 `refetchInterval` 函数 ↔ sqlc 的哲学,声明意图、机制交给工具
- 实时通道可以 best-effort,前提是持久层可以补课

## 阶段 6:人工介入 + 危险工具

**目标:** 把最危险也最有用的能力(shell)安全地交给 agent:审批闸门、子进程管理、副作用幂等。

### 设计思路

**核心决策 1:暂停是数据库状态,不是内存阻塞。** 审批等待可能数小时,goroutine 阻塞在 channel 上等 = 重启即丢,与可靠性承诺矛盾。正确形态:写 `approval_requested` 事件 + `status=waiting_approval` + **goroutine 直接退出**。三个白捡的性质:等待期零资源占用;崩溃免疫(它不是孤儿,恢复器只捞 running,它合法地躺着);审批历史天然可审计(谁、何时、批了什么都是事件)。

**核心决策 2:拒绝是信息,不是终点。** 用户拒绝一个操作 → 写一条"已被拒绝,请换方式"的 tool_executed → 模型换策略继续。与 3.2 的错误哲学一脉相承:agent 的韧性建立在它能看到否定性反馈上。

**核心决策 3:安全防线要诚实标注强度。** 明确说清:没有容器隔离就没有真正的沙箱。当前三层现实主义防线——审批(主防线)、超时+取消、输出截断;把"工作目录限制"宣传成"沙箱"才是最危险的。进程级隔离记账。

### 亮点

- **可选接口 + 类型断言**表达"危险"能力(`Dangerous` 接口):不污染基础 `Tool` 接口,已有工具零改动——Go 的能力扩展惯用法
- **sentinel error 做第三种控制流**:`errSuspendForApproval` 表达"既非成功也非失败的退出",`errors.Is` 辨认(与 `io.EOF` 同款手法);Execute 的 switch 从两路变四路(成功/挂起/取消/失败),状态机长大但形状不变
- **审批状态从事件流重建**(`loadApprovalState`):requested/decided 配对扫描——没有为审批建新表,状态机上加两个事件类型而已,架构自洽的又一次红利
- **时序闭合的推理**:挂起时对话历史带着未回应的 tool_call,但挂起期间不调 LLM;恢复后先补齐所有 tool 回应(批准的执行、拒绝的写拒绝文本)再调 LLM——协议的"每个 tool_call 必须有回应"约束在任何时刻的 LLM 调用前都成立
- **context 树第二层落成**:`WithTimeout(runCtx, 60s)`——父取消株连子(用户取消→子进程毫秒级被杀),子超时不上溯(单条命令超时→模型收到信息换策略,run 活着)。4.4 的预告全部兑现,`exec.CommandContext` 是取消机制的终点站
- **环境变量白名单**:不设 `cmd.Env`,子进程继承全部环境,模型一句 `env` 就能把 `LLM_API_KEY` 读进对话历史→数据库→前端。一行白名单防住真实 agent 产品泄露过的坑
- **truncateMiddle 保首尾截中间**:命令输出的头(表头)和尾(汇总/报错)信息密度高于中段——截断策略也有领域知识
- **副作用幂等的解法谱系**(按代价):引导模型写幂等命令(system prompt 一句话)< 执行前指纹(`tool_started` 意图先落库,恢复时发现孤悬 started → 转人工:"状态未知,是否重跑?")< 两阶段工具(金融级才值得)。采用 1+2,且方案 2 复用 6.1 的审批机制——**不确定时把决定权还给人**
- 给模型的 description 传递使用策略("合并操作减少审批打扰")——prompt 工程优化的是人机协作成本

### 难点/踩坑

- 审批 API 的"写事件+改状态+重启"非原子,中间崩溃留中间态——诚实记账(事务包裹,`DBTX` 接口早已备好),阶段 7 加固
- SIGKILL 只杀直接子进程,`sh -c` 的孙进程可能变孤儿——进程组/容器记账
- handler 绕开引擎的 append 封装直接写事件——分层的小破窗,同批加固

### 沉淀原则

- 长时间等待的正确形态永远是"持久化状态 + 事件唤醒",不是"阻塞的执行流"
- 危险能力的安全 = 多层防线各自诚实 + 人在关键路径上
- 新功能优先问:能不能表达为状态机上的新事件?能,则恢复/重放/审计全部免费
